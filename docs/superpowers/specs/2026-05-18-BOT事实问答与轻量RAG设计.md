# BOT 事实问答与轻量 RAG 设计

日期：2026-05-18

## 1. 背景

本项目的北极星目标是让 AI Boot 在飞书群里承担训练营运营助教职责：能回答学员问题、解释得分与晋升、激励互动学习，并把天梯榜作为持续运营工具。当前用户反馈的核心问题是 BOT 在被 @ 后经常答非所问，尤其是段位、分数、C/S 互动分、规则解释和漏分核对类问题。

本设计只以服务器运行版本和服务器真实数据为依据，不以交接文档作为事实来源。已核对的服务器事实包括：

- 当前运行链路已有短期上下文：触发用户最近 5 条发言、群聊局部上文最多 15 条，但该上下文只在进程内存里，服务重启会丢失。
- 段位类问题已有一段确定性回复，但覆盖面窄，只能回答非常有限的段位状态问题。
- 其他规则、漏分、C/S 互动、课程上下文类问题仍容易落回通用 LLM。
- 服务器库中 S1 有少量已批准事件，C2 只有极少量已批准事件；`reaction_tracked_messages` 为 0，`raw_events` 中未看到 reaction-like 记录。这说明 C/S 链路不是完全不可用，但点赞/表情互动没有形成稳定、可审计、可解释的事件闭环。
- 当前榜单维度已经合并 v3 分，但 BOT 问答还没有统一读取同一套“榜单 + 规则 + 评分事件 + 上限”事实口径。

## 2. 目标

本次设计采用“先运营事实问答，再扩展课程/群聊上下文问答”的路径，目标如下：

1. BOT 回答段位、分数、漏分、规则、C/S 互动类问题时，必须基于数据库和规则事实，不允许模型猜测。
2. BOT 能解释“我为什么还是某段位”“我差什么分”“我的 C/S 有没有算”“哪条消息被计分或没计分”。
3. BOT 对课程、作业、上下文类问题可以使用轻量 RAG，但必须显式区分事实、上下文和推测。
4. C/S 维度必须被纳入同一套审计链路：事件接收、归属、写库、计分、榜单展示、BOT 解释都要口径一致。
5. 保持回复少而准，避免为了“聪明”而刷屏。

## 3. 非目标

本次不做大而全的知识库平台，不引入复杂向量数据库作为第一步；也不把所有群聊都长期暴露给 LLM。图片理解、模型切换、分数重放和段位公告仍沿用已有主线，只在必要处接入事实问答能力。

## 4. 推荐方案

采用“运营事实层 + 轻量 RAG + LLM 表达层”的组合。

不推荐只改 Prompt，因为目前的问题不是话术不足，而是回答时没有稳定事实来源。不推荐继续堆硬编码规则，因为每新增一种问法都要补规则，后续仍然脆弱。

推荐方案的原则是：

- 结构化运营问题先查事实，再生成回答。
- LLM 只负责表达和压缩，不负责计算分数、判断晋升、虚构规则。
- 事实不足时必须明确说明缺少什么，并提示可执行的下一步，例如“请转发那条消息给我核对”。

## 5. 架构设计

新增一条 BOT 问答流水线，放在现有 ChatEngine 前或内部重构为明确阶段：

1. `IntentRouter`：识别用户问题类型。
2. `FactProvider`：按意图读取真实运营事实。
3. `KnowledgeRetriever`：读取规则文档、得分攻略、课程资料和近期上下文。
4. `AnswerComposer`：用模板或 LLM 生成最终回复。
5. `AnswerAuditLogger`：记录本次问题命中的意图、使用的事实来源、回复路径和是否调用 LLM。

### 5.1 IntentRouter

需要识别以下意图：

- `level_status`：问当前段位、为什么没晋升、如何晋升。
- `score_breakdown`：问总分、维度分、分数变化。
- `score_missing_check`：问某条消息、图片、作业、点赞是否漏分。
- `cs_interaction_check`：问 C/S、点赞、评论、互助、表情互动是否计入。
- `rules_query`：问段位机制、天梯榜规则、Prompt 是否必须、得分攻略。
- `course_or_homework_qa`：问课程、作业、文件、上下文。
- `general_chat`：普通闲聊或轻运营回应。

运营事实类意图优先级高于闲聊。只要问题中包含“潜力股、段位、晋升、分数、天梯榜、C/S、点赞、互动、漏分、规则”等信号，就不能直接走通用 LLM。

### 5.2 FactProvider

FactProvider 提供稳定接口，统一读取：

- 成员身份、角色、是否参与榜单。
- 当前总分、排名、K/H/C/S/G 维度。
- 当前段位、下一段位、晋升路径和缺口。
- v2 与 v3 已批准评分事件。
- 每类得分的周期上限、已用额度和上限命中情况。
- 近期与用户相关的消息、图片、文件、表情互动、互助事件。
- 手动调分、撤销、补录等审计事件。

所有回答段位和分数的问题都必须通过 FactProvider，不再在 ChatEngine 中各处拼 SQL 或写死规则。

### 5.3 KnowledgeRetriever

第一阶段使用轻量检索，不引入向量库：

- 规则文档按章节切分，例如“段位晋升”“K/H/C/S/G 得分”“C/S 互动”“上限规则”“常见问题”。
- 用关键词和意图映射检索对应章节。
- 课程/作业问答先用触发用户最近 5 条发言、群聊局部上文、最近文件摘要；必要时再接课程资料章节。
- 图片上下文默认只使用已缓存的图片理解摘要，不在普通问答里临时重新识别图片，避免图片导致 100 秒级等待。

后续如果规则文档和课程资料明显变多，再升级为向量检索。

### 5.4 AnswerComposer

回答分三类：

1. 确定性模板：段位状态、分数拆解、C/S 事件核对、规则命中说明。
2. 模板 + LLM 润色：运营解释、晋升建议、得分攻略。
3. LLM 直接回答：课程理解、作业思路、普通聊天，但必须带事实块和“不知道就说明不足”的约束。

LLM 输入必须包含结构化事实块，例如：

- 用户当前：姓名、段位、总分、排名、维度分。
- 下一段位：可走路径、缺口、缺少维度。
- 近期计分事件：时间、类别、分值、状态、原因。
- 规则来源：章节名、规则摘要。

LLM 不允许自行计算分数。如果事实块没有相关信息，必须回复“我现在查不到这条互动/消息”，而不是泛泛鼓励。

## 6. C/S 链路设计

C/S 互动分必须单独修成可审计链路。

### 6.1 C 维度

C 维度包括 AI 作品、方法、Prompt、创意应用和被群友认可的作品互动。需要保证：

- 图片、海报、客户演示、工作流截图等可以进入 `ai_artifact` 或 legacy C 类。
- Prompt 不再是唯一硬条件，分享 AI 实践过程、产物和方法都可以得 C。
- 表情/点赞如果作为 C2，则必须能追溯到“谁给谁的哪条消息点了什么反应”。

### 6.2 S 维度

S 维度包括同伴互助、答疑、有效反馈、参与互评。需要保证：

- @ 同学并提供帮助、回答同学问题、纠错测试结果可以计入 S。
- 只 @ BOT 问自己问题不能误计为 S。
- S1、peer_help 和互评卡片的结果最终能在同一维度口径中展示和解释。

### 6.3 互动事件闭环

互动事件应形成以下闭环：

1. 接收飞书 reaction / mention / peer review 事件。
2. 写入原始事件表或新增统一互动事件表。
3. 解析原消息作者、互动发起人、所属群、时间和消息 ID。
4. 根据规则决定归属给原作者、互动者，或双方不同类别。
5. 写入评分事件并应用上限。
6. 榜单维度汇总。
7. BOT 可回答“这条互动有没有算、算给谁、为什么”。

这是本设计的硬要求。否则 Grace 类“我明明互动了为什么没分”的问题无法被可靠回答。

## 7. 数据与接口建议

优先复用现有表，必要时新增轻量表：

- `bot_answer_audits`：记录问答审计，包括 message_id、member_id、intent、facts_used、reply_mode、latency_ms、model。
- `bot_knowledge_chunks`：规则和课程资料切片，包含 chunk_id、title、body、tags、updated_at。
- `interaction_events`：如果现有 raw_events 无法承载 reaction 归属，则新增统一互动事件表，记录 source_message_id、actor_member_id、target_member_id、interaction_type、raw_payload、scoring_event_id。

接口上新增 `BotFactService`：

- `getMemberScoreStatus(memberId)`
- `getPromotionExplanation(memberId)`
- `getScoreBreakdown(memberId)`
- `getRecentScoreEvents(memberId, filters)`
- `getInteractionAudit(memberId, query)`
- `getRuleSnippets(intent, query)`

## 8. 失败处理

- 找不到学员：回复未匹配到榜单账号，并提示让学员本人 @ 或说明要查哪位同学。
- 找不到消息：说明无法定位具体消息，提示转发/引用原消息。
- 飞书 reaction 缺少 chat_id：仍要记录原始事件，并通过 message_id 查询或降级为待核对事件。
- LLM 超时：运营事实类问题使用模板回复，不因 LLM 超时失败。
- 规则文档缺失：回答数据库事实，并提示规则文档未命中，不编造条款。

## 9. 测试设计

测试必须使用现有群内消息和管理测试群验证，不用伪造理想数据替代真实链路。

最低测试集：

1. Grace 问“为什么我还是潜力股”：应返回真实总分、维度、下一段位缺口，并说明 C/S/G 情况。
2. 张本一问“如何能成为潜力股”：应识别为段位/规则类问题，不再泛泛聊天。
3. 学员问“我的 C/S 点赞互动算了吗”：应查询互动和评分事件，不得编造。
4. 学员说“不用加分”：应进入 opt-out 或撤回/核对路径，不得继续聊天式鼓励。
5. 管理测试群发送“审核”“管理”“调分”：仍应触发对应卡片，不能被问答链路吞掉。
6. 回放真实群消息：验证 score_candidate、learner_qa、score_opt_out、admin_command 的路由不会互相覆盖。
7. C2 reaction 事件：验证原始事件可落库、归属可解释、榜单维度可更新。
8. S1 / peer_help 事件：验证互助计分、上限、维度汇总和 BOT 解释一致。

## 10. 上线策略

上线分三步：

1. 先在管理测试群启用事实问答和审计日志，不影响正式群自动回复。
2. 用真实群历史消息回放验证路由、事实读取和回复质量。
3. 正式群开启运营事实问答；课程/作业类 RAG 可先保守启用，图片只使用缓存摘要。

上线后观察指标：

- 答非所问率。
- 运营事实问答命中率。
- LLM 回答中无事实来源比例。
- C/S 事件落库数量和计分数量。
- 学员追问“不是这个意思”的比例。
- BOT 每日主动消息数，防止刷屏。

## 11. 验收标准

本设计完成后，需要达到以下标准：

- 段位、分数、规则、漏分类问题不再直接走无事实 LLM。
- Grace、张本一这类问题能给出与榜单一致的解释。
- BOT 能说明 C/S 当前是否有记录、是否计分、为什么未计分。
- C/S 事件链路有可审计数据，不再只依赖内存或不可追溯日志。
- 管理命令优先级不被问答链路破坏。
- 所有 BOT 发消息测试先在管理测试群完成。
